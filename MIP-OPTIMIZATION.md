# MIP-OPTIMIZATION.md

Ниже — 10 направлений оптимизации для минимального пакетного менеджера **mip**. Пункты сформированы по архитектурным узлам, которые уже видны в кодовой базе: резолвер зависимостей, загрузка tarball, распаковка, кеширование, обработка lockfile, установка зависимостей по дереву и т.д.

---

## 1) Ускорить резолв версий: убрать лишние сортировки и повторные fetch
**Проблема (по коду):** в `lib/core/resolver.js` для каждого запроса диапазона берётся `versions` и сортируется: `Object.keys(pkgInfo.versions).sort(semver.rcompare)`. При большом числе зависимостей это даёт много CPU-работы.

**Оптимизация:**
- Кешировать полученный список версий и их отсортированную форму per `(name)`.
- Свести resolve к минимуму: предварительно подготовить `versionsSorted` один раз на пакет.
- Для `versionRange` без `latest` отдельно кешировать результат `maxSatisfying` (у вас уже есть `this.resolved` — но ключ лучше делать более нормализованным и расширить на «пакет → версии»).

**Что измерять:**
- время на `resolveVersion` (CPU)
- число обращений к registry

---

## 2) Параллелить разрешение дерева зависимостей (но контролируемо)
**Проблема:** `resolveVersion` рекурсивный и делает `await this.resolveVersion(...)` по каждой зависимости последовательно.

**Оптимизация:**
- Собирать зависимости в очередь и резолвить потом батчами через ограничитель параллелизма (например, `p-limit`-подобный механизм без лишних зависимостей).
- Использовать in-flight кеш уже на уровне `resolveVersion` (аналогично кэшу в `SuperCache`).

**Риск:** взрыв количества запросов к registry.

**Что измерять:**
- wall time установки
- нагрузку на registry (сколько запросов одновременно)

---

## 3) Ускорить загрузку tarball: streaming и/или reuse соединений
**Проблема (по коду):**
- `lib/core/parallel-download.js` собирает весь ответ в память: `responseType: 'arraybuffer'`, затем возвращает `data` целиком.
- распаковка обычно требует tar-файл/стрим.

**Оптимизация:**
- Перейти на streaming: pipelining `HTTP response -> tar extractor stream`, чтобы не держать массивы в RAM.
- HTTP/2: следить, чтобы один session переиспользовался и завершался корректно; добавить `goaway`/error handling и backoff.

**Что измерять:**
- пик RAM
- общий wall time

---

## 4) Убрать запись tarball в temp-файл в распаковке
**Проблема (по коду):** `lib/utils/cahce.js` (опечатка в имени файла) делает:
- `fs.writeFileSync(tempFile, tarball)`
- `tar.x({ file: tempFile, ... })`
- `unlinkSync(tempFile)`

То есть каждый раз запись на диск + чтение обратно.

**Оптимизация:**
- Если `tar` поддерживает поток, передавать tarball как stream/buffer без записи на диск.
- Если удобнее — кешировать извлечённые слои в disk cache и реюзить.

**Что измерять:**
- время extract
- количество операций записи файлов

---

## 5) Привести lockfile к «аппендам» + индексации для O(1) lookups
**Проблема:**
- В `lib/core/locker.js` есть `getInstalledVersion(name)` (сканирует `Object.entries(...)`), сложность O(n) по числу пакетов в lockfile.
- В `lib/commands/install.js` `getInstalledVersion` читает и парсит lockfile целиком для каждого рекурсивного шага.

**Оптимизация:**
- При установке один раз загрузить lockfile в память и передавать object вниз по рекурсии.
- Добавить in-memory индекс `name -> version` (или `packages` map).
- В lockfile хранить отдельный индекс секцию (или генерировать при загрузке).
- Сократить число `fs.writeFileSync`/`JSON.stringify` — обновлять батчами.

## 6) Детектор «что уже установлено» делать корректно (инкрементальность)
**Проблема:** текущий `installPackage` проверяет только наличие `installDir/package.json` и/или сравнение через `semver` диапазона на child dependency.

**Оптимизация:**
- Проверять не только `package.json`, но и lock-совместимость/целостность (в терминах mip-lock):
  - `resolved tarball` идентичный?
  - integrity/sha совпадает?
- Делать «skip install» на основании lockfile + integrity, а не только FS-наличия.

**Что измерять:**
- доля пропусков при `mip install` повторно

---

## 7) Устранить лишние синхронные I/O на установке
**Проблема (по коду):** `lib/commands/install.js` использует `fs.readFileSync`, `fs.writeFileSync`, `execSync` и т.д. У вас рекурсия + синхронные операции — это блокирует event loop и снижает эффективность параллелизма.

**Оптимизация:**
- Перевести критические пути на async FS (`fs.promises.*`).
- `execSync tar -xzf` заменить на библиотечную асинхронную распаковку (или worker-thread).
- Подход: асинхронная распаковка + лимит параллельности по disk I/O.

## 8) Сделать SuperCache ближе к «кешу пакетов», а не только JSON
**Проблема:** `lib/core/super-cache.js` — disk cache пишет JSON `*.json`. Но tarball/инсталл-артефакты большие.

**Оптимизация:**
- Разделить кеши:
  - metadata cache (JSON)
  - artifact cache (tarball/extracted) — можно хранить бинарно (streamed) или pack-слоями.
- Добавить cleanup по размеру/TTL и atomic writes (tmp + rename).

**Что измерять:**
- hit rate по metadata и по artifacts
- размер кеша

---

## 9) Оптимизировать рекурсивный install: один проход вместо глубокого re-parse
**Проблема:** в `installPackage` рекурсивно вызывается `installPackage(depName, depRange, options);`, и на каждом шаге могут заново парситься файлы (`mip-lock.json`) и идти peer-resolution.

**Оптимизация:**
- Построить DAG установок один раз (после резолва) и затем исполнять план.
- Свести peer-resolution к одному проходу с кешированием результатов.
- Разнести «планирование» и «выполнение»: планирование делает сеть/резолв, выполнение делает FS.

---

## 10) Улучшить parallelism в реальной установке (а не только download)
**Проблема:** параллельная загрузка реализована как отдельный core, но `install.js` по сути ставит зависимости последовательно (for..of с await).

**Оптимизация:**
- Использовать параллельную загрузку/извлечение на уровне батчей, но с лимитом по:
  - количеству одновременных сетевых запросов
  - количеству операций disk extract
  - количеству child dependencies, чтобы не перегружать system.

**Что измерять:**
- wall time установки проекта с множеством пакетов
- деградация на HDD vs SSD
